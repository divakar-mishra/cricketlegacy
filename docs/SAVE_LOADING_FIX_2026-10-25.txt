SAVED CAREER LOADING — IMPLEMENTED SOURCE FIX
25 October 2026 | Source changes, not a new installed app or store artifact

WHAT CHANGED
============
Saved Games and the main-menu Continue preview now read a small, versioned,
encrypted per-slot summary instead of opening every full cricket world. The
summary contains display labels/date/season/wallet and VIP display hints, not
players, fixtures, history or a playable SaveGame. There is no mutable full-world
cache shared between UI, backup and gameplay.

The summary uses the existing device-local slot key, AES-256-GCM and a separate
summary-only authenticated-data context. It cannot be substituted for a playable
save or copied to another slot. Key loss/tampering fails closed. Primary saves,
checksums, rolling backups, legacy migration and write serialization remain.

Writes/import replacements/recovery/deletion invalidate old summaries BEFORE
changing playable copies, then publish derived metadata after the primary commit.
Failure to publish a summary does not turn a durable purchase/save into a failed
purchase/save. Missing/corrupt/older-schema summaries fall back to verified full
loading. Occupancy is checked independently: a missing summary is NEVER an empty
slot. Existing slot-selection and paid deletion/pending-purchase guards remain.

Play, Continue and Delete first open the actual selected career and verify its
mode/save identity. Summaries never activate gameplay, grant an entitlement,
authorize a destructive operation or decide creation eligibility. Duplicate
Play/Continue taps are guarded and show an opening state. Switching tabs, Back
or leaving the screen invalidates pending action results, including an away-and-
back-to-the-same-tab race. A backup status refresh does not cancel a deliberate
selected-career open while the screen remains focused.

CANCELLATION AND BACKUP
=======================
List/selected reads check cancellation before queued work, between primary and
backup, between slots, and before publishing. Lists yield between slots, letting
input and queued saves proceed. Native crypto already in flight and synchronous
JSON/migration work cannot be preempted midway; this is bounded abandonment, not
a promise that every instruction stops at the instant Back is pressed.

Account backup/recovery scans the small summaries. A confirmed unchanged local
token avoids another full-world open/checksum/migration/VIP sync. The token is
bound to account, mode, slot, save ID, local generation and the remote/local
acknowledgement checksums/revision. Older clients retaining unknown fields cannot
keep a token valid after changing those acknowledgements. Cold verified scans
record the existing cloud checksum contract in the protected summary, avoiding
a second full read just to establish the first token for unchanged backups.

Dirty bound careers are opened once in the upload loop, not during a whole-mode
scan followed immediately by another upload read. A changed token still forces
verified inspection even if the dirty journal hook failed. New writes during
uploads remain pending; follow-up requests and recover=true are not discarded.
Account switch/sign-out/teardown cancels queued reads and rejects late recovery.
The cloud checksum algorithm, remote conflict/deletion contract and provider
configuration have NOT changed. Purchase/restore fulfilment is not replaced by
index data, and consumables are not re-granted.

LOADING CHANGE AND SAFETY
========================
Both creation handlers previously awaited listSlots(mode), which sequentially
loaded all six slots. Occupied careers were decrypted, migrated and passed to
the local VIP archive before creation could even select a destination.

findCreationSlot now checks primary/backup occupancy and stops at the first
empty base slot. A chunk manifest alone means occupied; chunks are not loaded
or parsed to check occupancy. Damaged JSON/null, broken manifests, backup-only
slots and read errors are never treated as free. Requested slots are bounded
and checked explicitly. Extra slot six still requires the existing mode-scoped
VIP/legacy-pass rule, using full verified save loading only for that uncommon
case. Normal Saved Games listSlots/loadSave behavior is unchanged.

Selection waits behind pending operations on the slot. writeSave rechecks
identity inside the existing queue and refuses another career that won a race.
Encryption, checksums, rolling backups, cloud-dirty journal and durable first
write are retained. Home opens only after writeSave + last-played pointer, then
activation. No pretending the career is saved while a background write runs.

Manager now also has a synchronous duplicate-tap guard (Player already had it).
Creation's own Back controls ignore taps during the first write. Both footers
explain the spinner with 'Creating and saving your career…'. The spinner is
retained while genuine world creation/encryption/storage is underway.
No new save schema, game balance, grants, provider/native config or dependency.

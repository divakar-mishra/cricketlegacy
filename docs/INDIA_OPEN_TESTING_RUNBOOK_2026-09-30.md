## From project to this review stage

For each step, check the outcome before moving on. Exact Console labels may change.

1. **Set up the app and account.** Create the Play Console app as a game with package `com.coverdrive.cricket`; keep the Play app, Expo/EAS project, upload signing key, AdMob app, RevenueCat Android app, and publisher/legal site associated with that same package. Why: Play fixes the package name after the first upload, and mismatched package/product configuration prevents services from working. Outcome: one stable app identity. Do not put credentials, service secrets, or signing keys in this runbook.
2. **Complete app content and legal setup.** Fill Play's target audience, ads, Data safety, content rating, app access, privacy policy, deletion, and contact fields based on the actual shipped behavior. The approved product policy is **18+ in India, 13+ elsewhere; not directed at children**. The four public legal routes and their build-time variables are documented in [STORE_LEGAL_COMPLIANCE.md](STORE_LEGAL_COMPLIANCE.md); review that file's historical notes against current source before reusing a declaration. Why: Console answers must agree with the bundle and public policies. Outcome: app setup/review requirements have no unresolved blockers. Do not equate target-audience age with the separate IARC content rating.
3. **Configure production services, without exposing secrets.** Verify EAS `production` environment contains the intended public RevenueCat Android key, legal URLs, Supabase configuration if enabled, and production AdMob unit IDs; verify Google Play in-app products/prices and RevenueCat product mappings, offerings, and entitlements. Guest purchases should not require signing in to this app, but they still require Play Billing availability. Check AdMob app review, policy/consent configuration and `app-ads.txt` separately. Why: embedding SDKs or product IDs alone does not prove prices, checkout, ad approval, or fills. Outcome: dashboard configuration agrees with the app's product IDs and policy. See [IAP_CATALOGUE_FINAL.md](IAP_CATALOGUE_FINAL.md) for the launch catalog.
4. **Run local release gates.** On the intended commit, run `npm run check:release`, inspect any failures, then test both careers, saves/relaunch, age/consent paths, purchase error states and ads with test devices. Use [RELEASE_GATE_2026-09-29.md](RELEASE_GATE_2026-09-29.md) as a historical test record, **not** as proof code 12 passed all code-11 checks. Why: a successful build does not validate gameplay or policy behavior. Outcome: a dated test record with known remaining issues. Do not delete real player saves to test destructive flows.
5. **Build the store artifact, not a QA APK.** The [EAS production profile](../eas.json) has QA tools off, uses an Android App Bundle and remote auto-incremented version codes. The command for a *future* release is `eas build --platform android --profile production`; inspect the resulting manifest, package, version name/code, upload certificate, and release environment before upload. The accepted artifact for this submission is [code 12](../output/cricket-player-manager-production-v1.0.8-code12.aab), shown by Play as `12 (1.0.8)`, min API 24+, target SDK 36. Why: the preview/QA APK is not the Play upload and a reused version code is rejected. Outcome: a signed, unique AAB. Note: `app.json` currently says `android.versionCode: 8`, while EAS uses remote app versioning; Play reads the uploaded bundle's code, not that local JSON field.
6. **Meet testing/account access requirements.** This app completed its closed-test period and the owner received production-access approval. For a new personal developer account to reproduce that stage, follow Google's closed-testing eligibility/production-access process and gather genuine tester feedback; approval is not the same as a production release. Why: account-level access can block later tracks. Outcome: Console permits the intended track. [Google's requirements](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en) are authoritative for current eligibility.
7. **Set India availability and open-test testers.** In Play Console, select India in country/region availability and confirm the Open testing track's Countries tab says **India targeted**. Select **Unlimited** testers on its Testers tab and provide a feedback email/URL if desired. Initially this Console showed an open-testing restriction; adding India to production *country availability* and syncing the open track removed it, even though Production had no release. Do not generalize that one UI state into a rule that India requires a production launch. Why: the country and tester settings determine who can opt in. Outcome: India targeted, unlimited testers. “Anyone” still means an eligible Google Play user on a supported device, not literally every Android device.
8. **Prepare the public listing.** Go to Grow users → Store presence → Store listings → **Edit default listing**. The owner submitted the title `Cricket: Player & Manager`, short description `Build your cricket career or manage a club. Train, compete and win.`, full description, corrected phone screenshots and feature graphic. The local [listing draft](../marketing/play-store-final-2026-09-28/PLAY_STORE_LISTING.md) has a *different* short description; use the owner-confirmed Console text as the record of this submission. Check image order, no QA/debug UI, age/store claims, supported features and spelling before saving. Why: open-test users can see the listing, and listing edits undergo review. Outcome: five default-listing changes queued/submitted. Local marketing assets are source material, not proof of which exact images Play accepted.
9. **Create the open-test release.** Go to Test and release → Testing → Open testing → Create new release. Upload the [code-12 AAB](../output/cricket-player-manager-production-v1.0.8-code12.aab) (or select it from Play's library if already uploaded). Release name: `1.0.8 – India Open Test`. Submitted release notes: `Initial open test of Cricket: Player & Manager. Play both careers and share feedback on gameplay, Store purchases, ads, and stability.` Click **Next**, inspect errors/warnings, then **Save**. Play showed one warning: no R8/ProGuard deobfuscation file. That warning did not block this submission; add a mapping file in a later build if code shrinking produces one. Outcome: a release saved to Publishing overview, **not yet necessarily public**.
10. **Submit the intended changes for review.** On Publishing overview, inspect the exact change list before clicking **Submit changes for review**. Submission 4 included India production country availability and the open-test rollout; it later showed Published. The track was nevertheless paused, so the owner resumed it and grouped that action with the five listing edits in submission 5. The early-access track's two changes were **Save for later**, not part of submission 5. Why: saving a release, passing quick checks, being in review, and becoming available are different states. Outcome: submission 5 was previously shown In review; the later Oct 2 track screenshot shows **Active** and the open-test release **Available to unlimited testers**. Managed publishing was off. Check Submission activity separately for the listing's final review status.

3. On the **Testers** tab, copy the Android/web opt-in link. On a compatible device with an India-eligible Play account **not enrolled in internal testing**, opt in and install through Google Play. 4. On that Play-installed build, open the Store **without app sign-in** and check each product's localized price. The owner has now reported one successful ₹99 purchase; record its product ID, test/real charge status and whether its benefit survives relaunch when available. Add dedicated accounts to Play **License testing** before making test purchases; ordinary open testers may be charged real money. [Play Billing testing](https://developer.android.com/google/play/billing/test)
5. Test ads separately on approved test devices: consent/age branches, banner/interstitial/rewarded placement and reward only after completed viewing. Verify AdMob app review and request/fill data; a “Test Ad” or correct ad-unit ID is not proof live ads serve. Check Android vitals, crash reports, support/deletion requests and Play policy notices during open testing. Do not “publish and forget” for a year.

## Known traps and unfinished items

- **Production country ≠ production release.** India being present in Production availability does not mean the app launched to all users in Production. The Production release dashboard still showed Inactive/no release.
- **Early access is not the open test.** Its track is inactive with no releases. Two changes are saved for later. If the goal is a clean Console, review and discard those exact pending items from Publishing overview when safe; do not discard the open-test/listing changes by mistake.
- **Price unavailable / Coming soon** was observed on the earlier sideloaded APK. The Oct 2 owner report now establishes a successful ₹99 purchase and the screenshot shows a ₹449.00 VIP price; keep the remaining product and recovery checks open.
- **Device support is finite.** The Console showed 19,191 supported Android devices for this release, not every Android device in India.
- **Version 1.0.8/code 12 is already uploaded.** A code change requires a new AAB and higher version code; do not attempt to edit an uploaded bundle in place.
- **Play says the open test is available, but delivery/commerce are unverified.** Record a working opt-in link, Play-delivered version code, billing results and ad-review/request evidence before calling the entire launch verified. Open testing is not the same as a general Production release.

WHY THE LIST IS SLOW
===================
1. Full careers are opened for summary labels.
   SavedGamesScreen.refresh awaits listSlots(mode). SlotView carries a whole
   mutable SaveGame; rendering only needs a name, team, season, date and state.
   listSlots loops over all six slots sequentially, awaiting loadSave each time.
   No result array is delivered until the last slot finishes. One expensive
   career or unreadable copy delays the entire first list.

2. Every ordinary load reads BOTH primary and rolling backup.
   loadSave unconditionally awaits readCopy(primary), then readCopy(backup),
   even when primary is healthy. Each nonempty modern copy goes through storage
   reassembly/JSON, key lookup, AES opening, UTF-8, JSON and integrity checking.
   Both readable legacy copies are migrated before sealing the legacy gate.
   It then checks the sealed marker, runs migrations and awaits local VIP sync.
   Thus six occupied Player slots with two copies mean twelve full opens.
   Encryption itself is required; unnecessary repetition is the target.

3. The screen and background backup duplicate the same work.
   Account recovery opens both modes using listSlots, even in a normal backup
   pass with no missing careers. It may reload pending careers again for upload.
   MainMenu getLastPlayed simultaneously opens the selected complete career.
   loadSave serializes by slot for safety, but does NOT share identical requests:
   the next consumer repeats the open after the previous consumer finishes.
   Background reads can therefore delay foreground reads AND queued writes.

4. Focus, tab changes and backup completion reload again.
   Saved Games' focus callback depends on backupRefresh. Successful OR failed
   backup completion increments refresh, causing another focused list load.
   MainMenu also reopens getLastPlayed on focus/backup refresh.
   Switching Player -> Manager -> Player reads Player again; there is no
   independent retained per-mode verified listing cache.
   refreshRequest/selectedMode correctly reject stale results/actions, but do
   NOT stop the underlying listSlots loop or an already-running loadSave.
   Back/tab switching can leave unused work executing after the screen changes.

5. A running backup can acquire a second full pass.
   queuedJob is cleared when runBackup starts. A request during that active pass
   queues a follow-up; further queued requests share that follow-up. This is
   not an infinite loop, and a follow-up can be necessary for new writes or a
   recover=true request. It nevertheless multiplies work when no new data exists.

6. Large-save synchronous work remains outside the yielding UTF-8 helper.
   Checksums/stringification, base64 transport conversion, JSON parse, migrations
   and activation still run on JavaScript. Backup compares/checksums every
   loaded save and prepares pending snapshots/content hashes. writeSave clones
   via JSON.stringify/parse BEFORE entering the queued operation, then serializes
   the protected envelope. Async functions do not move these portions off JS.
   checksumOf(JSON.stringify(save)) also stringifies the string internally;
   this existing cloud checksum contract must NOT be casually changed.

IMPACTS AND NON-FINDINGS
=======================
User experience: blank/loading lists, late Continue card, repeated waits on tab
changes, input/animation pauses and a misleading impression that careers vanished.
Existing race guards hide old-mode Play/Delete actions while new mode loads;
this safety is correct and must not be removed merely to reveal buttons sooner.

Resource pressure: a list retains full SaveGame objects; backup retains both
modes; MainMenu retains its resume save. During reads there are ciphertext,
base64/bytes, plaintext, chunk strings, parsed primary/backup objects and
checksum strings. More careers/larger worlds multiply work and temporary
allocations. This is a confirmed allocation pattern, NOT measured RAM growth,
a proven leak, OOM, ANR, memory-warning kill or battery-drain measurement.
No history pruning/deletion is proposed; old records must be preserved.

Data/purchases: no new corruption, lost career, duplicate reward, charge or
wrong-account grant was reproduced by this audit. Per-slot serialization,
backup fallback, tamper checks, ownership and payment-idempotency guards remain
necessary. A long critical-write spinner is not permission to dismiss the
screen, clear data or announce success before durability.

Network: local listing is already expensive even without a cloud round trip.
Backup does validate identity/network and has its own timeout; ordinary load's
VIP sync awaits local/session archive work while optional remote merge is not
awaited (explicit restore is different). Not simply an internet/Unity ads issue.
An unchanged confirmed backup still scans local worlds; avoiding uploads via
content hashes does not avoid those reads.

Platform: shared JavaScript/storage architecture exposes both Android and iOS.
The quoted timings are historical iPhone only. Current Android QA28 creation
improvement is recorded separately in COMPACT_CREATION_AND_LOADING_2026-10-25.txt;
do not claim frozen iPhone QA4 contains later root changes or Android timings.

RECOMMENDED FIX ORDER — NOT IMPLEMENTED BY THIS AUDIT
===================================================
1. Separate a small derived list/Continue summary from full-world opening.
   Populate/update it only after confirmed saves/recovery. Show summaries fast;
   verify the selected actual career/slot before Play or destructive actions.
   Missing/corrupt/stale metadata must never mean empty, grant VIP, override an
   owner, or hide intact primary/backup data. Legacy fallback is required.
2. Coordinate foreground reads and backup; share immutable verified work or
   generation-aware snapshots, not a mutable SaveGame object across consumers.
   Avoid redundant same-generation rereads and completion refreshes when local
   slot content did not change. Never delay durable dirty-journal recording or
   discard a follow-up needed for new writes, recover=true or an account change.
3. Stop unused list work between slots after Back/tab change; retain the current
   stale-result/mode guards. Optionally present verified rows incrementally.
4. Profile checksum/serialization/critical-write/activation separately, then
   reduce traversals or schedule bounded work while preserving EXACT existing
   checksum bytes, AES/AAD, format, migrations and transaction ordering.
5. Retest cold/warm lists with 0/1/6 careers per mode, many-season large saves,
   primary/backup failures, rapid tabs/Back, active backup, account switching,
   offline retry and foreground transitions. Measure first useful row and all
   rows separately from input latency; include peak memory and critical writes.
   Purchases/restore need explicit sandbox authority, not a real-charge test.

Do not solve this by removing backups/encryption/checksums, marking read errors
as empty, dropping history, launching every full-world load concurrently, or
returning cached mutable/foreign-account saves. More parallel full loads can
increase peak memory and input pressure despite improving one wall-clock span.
